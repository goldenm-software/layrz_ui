# Localization Architecture

**Status**: Implemented in DESIGN-73. All 133 keys with English defaults, comprehensive test coverage (94.1%), zero Material/Cupertino dependencies. DESIGN-64 pass 2 added a 14-key months/meridiem namespace on top of this baseline (see "DateTime Helpers — Weekday & Month Names" below); the totals in this document predate that addition and are not reconciled here.

## Overview

This document defines the localization contract for layrz_ui — the abstract interface through which all design system components access user-visible strings. The contract is decoupled from layrz_models to allow the package to work with or without that dependency, while providing a clean adapter for applications that already use `LayrzAppLocalizations`.

**Key principle**: layrz_ui defines the strings it needs; consuming applications decide how to provide them.

---

## Architecture

### Design

One **abstract contract** satisfied two ways, registered at the root `LayrzApp` and read throughout via `LayrzUiL10n.of(context)`.

- **`LayrzUiL10n`** — abstract class declaring every user-visible string in the design system. All components depend on this contract, never on layrz_models directly.

- **Two implementations**:
  1. **Custom implementation**: A consumer subclasses `LayrzUiL10n` and supplies their own strings. Useful for apps not using layrz_models, or those that prefer custom wording.
  2. **`LayrzModelsLocalizations`** — adapter that auto-fills from a `LayrzAppLocalizations` instance (the i18n object from layrz_models). Apps already using layrz_models get localization for free; no boilerplate required.

- **Built-in default**: `LayrzUiL10nDefault` implements `LayrzUiL10n` with English text. Follows the Flutter pattern of `DefaultMaterialLocalizations`. Automatically used when nothing is provided. This means:
  - The package works with zero configuration.
  - The example app needs no localization wiring.
  - Widget tests do not need to provide localization for each test.

### Wiring via LocalizationsDelegate

The contract is wired through **Flutter's localization delegate machinery**, not a bare `InheritedWidget`. This approach:

- Plugs into `MaterialApp` / `CupertinoApp` / custom apps via the standard `localizationsDelegates` list.
- Automatically rebuilds dependents when locale changes.
- Composes cleanly with other delegates (including `LayrzAppLocalizations.delegate()` from layrz_models).
- Matches the pattern layrz_models already uses, keeping the adapter thin.

**Access in components**:

```dart
final localizations = LayrzUiL10n.of(context);
final cancelText = localizations.actionCancel;
```

Or, for convenience, via extension on `BuildContext`:

```dart
final cancelText = context.l10n.actionCancel;
```

### Why This Shape

**Decoupling**: layrz_ui does not depend on layrz_models. It declares what strings it needs; layrz_models (if present) provides them through the adapter. Apps without layrz_models can still use layrz_ui by extending the abstract.

**Type safety**: Every string is a named member of the abstract, not a magic key in a map. IDEs complete member names; typos are caught at compile time.

**Locale changes**: Flutter's `Localizations` rebuild dependents automatically. No manual wiring of `InheritedWidget` needed.

**Consistency**: This pattern mirrors how `LayrzTheme` works (an `InheritedWidget` read via `LayrzTheme.of(context)`), so the API feels familiar.

**See also**: Decisions [D2 and D10 in `decisions.md`](decisions.md) — the layrz_models audit found `LayrzAppLocalizations` entirely Material-free, defined in `lib/src/i18n/src/engine/delegate.dart`.

## String Contract

This section enumerates all user-visible strings needed by layrz_ui components, organized by logical namespace. Each row in the tables below shows:

- **Key**: internal member name in the abstract class (e.g., `actionCancel`)
- **English default**: the text used when no localization is provided
- **Notes**: parameterization, pluralization, dynamic keys, or component scope

### Counting Rule

This contract uses an explicit counting rule to ensure all totals are verifiable:

1. **Distinct keys**: A key with singular and plural FORMS counts as **one key**. Both English forms are shown in tables for implementer clarity.
2. **Dynamic keys excluded**: Runtime-constructed keys like `dynamicAvatarTypes${type}` and `requiredFieldsTypes${field}` are NOT counted as fixed keys; they appear in a separate section.
3. **Parameters not counted**: Non-localization string parameters (e.g., `ThemedTable2.actionsLabelText`) are counted separately in a dedicated section.
4. **Overlapping time units**: Keys like `helperYear`, `helperMonth`, etc. overlap in meaning with `helperDurationDay`, but are **distinct keys** in source code and both are counted.
5. **Arithmetic shown**: Every section total is the sum of its rows; the grand total is the sum of per-section totals. This allows readers to verify consistency.

**Key verification**: All keys below have been verified to exist in layrz_theme source as dotted-string keys in `translations` map literals (e.g., `'layrz.calendar.today'`, `'actions.cancel'`).

## String Parameters (Component Configuration, Not Localization)

Some components accept user-visible string parameters that are **not** translation keys but **string literals** or callback results. These do **not** belong in `LayrzUiL10n`:

- **ThemedTable2**: `actionsLabelText`, `loadingLabelText`, `multiSelectionTitleText`, `multiSelectionContentText`, `multiSelectionCancelLabelText`
- **ThemedSearchInput**: `labelText`

**Design decision needed**: layrz_theme mixes localization keys, i18n keys, and plain string parameters for the same function. layrz_ui should pick one mechanism (see Design Problem #7 below).

## Design Problems: Open Questions

The following design issues require team discussion. Do not implement until these are resolved.

### 1. Dynamic Keys

**Problem**: Strings like `helpers.dynamicAvatar.types.$type` and `requiredFields.types.${field.toJson()}` are constructed at runtime. An abstract class cannot express these as typed members without either:
- **Option A**: Enumerate every possible variant (brittle if variants change; violates DRY).
- **Option B**: Retain a typed `String t(String key)` escape hatch for dynamic keys (weakens type safety that motivated the abstract).

**Decision needed**: Which trade-off? Or is there a third option (e.g., a companion `Map<String, String>` for dynamic variants)?

### 2. Parameterised Strings

**Problem**: Keys like `monthPickerYear` need methods with arguments, not getters:
```dart
// Not: localizations.monthPickerYear (incomplete)
// But: localizations.monthPickerYear(2024)
```

**Decision needed**: Should the abstract define parametric methods with signature like `String monthPickerYear(int year)`? How do adapters fill these — via string templates, format strings, or `intl` patterns?

### 3. Plurals

**Problem**: Eight duration units (day/days, hour/hours, etc.) need count-aware methods. `LayrzAppLocalizations.tc()` handles this, but a consumer extending the abstract by hand must implement plural logic themselves. This is locale-dependent and non-trivial.

**Options**:
- Provide plural logic via `intl` package (pure Dart, safe).
- Require adapters to implement plural rules themselves (burden on consumer).
- Defer plurals and ship English-only for now.

**Decision needed**: Which path?

### 4. Scope of Initial Contract

**Problem**: Of the 133 keys above, several belong to components that are dropped or blocked:
- **Map** (3 keys) — flutter_map is Material-built, feature blocked.
- **Code Editor** (2 keys) — code editor component is out of scope.
- **Required Fields** (19+ keys) — dynamic subsystem, scheduled late.
- **Table Paginator** — some keys may belong to the deprecated legacy table, not `ThemedTable2`.
- **Taskbar `toggleTheme`** — presumes light/dark toggle; dark mode is out of scope (D7).

**Decision needed**: Should the initial contract cover only in-scope M1 components? How do we grow the contract later without breaking implementers who extended the abstract? (Adding an abstract member is a **breaking change** for any subclass.)

### 5. Rich Text

**Problem**: `LayrzAppLocalizations.te()` returns a `TextSpan` for rich text (inline styling, links). Does the layrz_ui contract need rich-text members, or is plain text sufficient for the design system's own strings?

**Decision needed**: Include rich-text variants in the abstract?

### 6. Formatting (Not Just Strings)

**Problem**: Date formats, decimal separators, first-day-of-week, and month/weekday names vary by locale. `DateTimeExtension.format()` and `ThemedDecimalSeparator` already live in that space. These are **formatting decisions**, not **localized strings**.

**Decision needed**: Does locale-dependent **formatting** belong in `LayrzUiL10n`, or is it a separate concern (e.g., a `LayrzLocaleFormatting` interface)?

### 7. String Parameter Inconsistency

**Problem**: layrz_theme mixes three mechanisms for the same UI job:
- Translation map keys (e.g., `"actions.cancel"`)
- i18n keys (e.g., passed to `LayrzAppLocalizations.t()`)
- Plain string parameters (e.g., `actionsLabelText` on a widget)

**Decision needed**: Should layrz_ui standardize on one mechanism? If so, which? (This affects the design of every component that needs user-visible text.)

### 8. Component-Level Translation Override

**Problem**: layrz_theme has an `overridesLayrzTranslations` flag on every component with a translations map. Semantics unclear; need to confirm from source.

**Decision needed**: Should layrz_ui retain per-component translation override, or rely solely on the delegate mechanism? If retained, what does it do?

## How Components Consume Localization

### Pattern: Reading Strings in Widgets

All components read localization via `LayrzUiL10n.of(context)` or the convenience extension `context.l10n`:

```dart
// Illustrative design sketch — NOT production code

import 'package:flutter/widgets.dart';
import 'package:layrz_ui/localization.dart';

class ThemedButton extends StatelessWidget {
  /// The button label. If null, uses localized default.
  final String? label;

  const ThemedButton({this.label});

  @override
  Widget build(BuildContext context) {
    final localizations = LayrzUiL10n.of(context);
    final text = label ?? localizations.actionCancel;
    return GestureDetector(
      onTap: _onTap,
      child: Text(text),
    );
  }
}
```

### Pattern: Locale Changes

When the user changes locale (via `Localizations.localeOf(context)`), Flutter's `Localizations` system rebuilds all `of(context)` dependents automatically. No manual wiring required.

```dart
// When user taps "Settings" → changes locale → returns
// → Flutter calls didChangeLocales() → rebuilds all dependents
// → every LocalizationsDelegate rebuilds → LayrzUiL10n.of() returns new instance
// → all components rebuild with new text
```

### Pattern: Testing

Widget tests do not need to provide localization; `LayrzUiL10nDefault` is automatic:

```dart
// Widget test — localizations work out-of-the-box

testWidgets('Button shows cancel text', (tester) async {
  await tester.pumpWidget(
    LayrzApp(
      home: Scaffold(
        body: ThemedButton(label: null), // Will use localized "Cancel"
      ),
      theme: LayrzThemeData.light(),
    ),
  );
  expect(find.text('Cancel'), findsOneWidget);
});
```

## Built-in English Defaults

Every one of the 133 keys already has an English fallback in layrz_theme source. `LayrzUiL10nDefault` is largely a matter of collecting this existing copy rather than authoring new text.

Benefits:
- The design system works out-of-the-box with zero configuration.
- No special setup in the example app.
- Widget tests pass without localization wiring.
- A strong English baseline for translators.

See the [migration-gap.md](migration-gap.md) for a full inventory of existing layrz_theme strings and their sources.
